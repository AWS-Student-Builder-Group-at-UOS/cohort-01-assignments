# Session 04 · 컨테이너 기반 마이크로서비스 전환

- **세션 일자:** 2026-11-24
- **제출 마감:** 2026-12-08 21:00 (KST)

서버에서 직접 운영하던 애플리케이션을 컨테이너로 옮기고, 기능별로 독립적으로 배포·확장하는 구조를 설계합니다. 수동 SSH 배포와 평문으로 저장된 비밀번호의 문제를 짚고, 배포 자동화·권한 분리·자격 증명 관리·배포 실패 시 롤백을 함께 살펴봅니다.

## 학습 목표

- **컨테이너 기초:** 하드웨어를 가상화하는 VM과 OS 커널을 공유하며 실행 환경을 격리하는 컨테이너의 차이를 설명합니다. Dockerfile로 이미지를 만들고, 그 이미지를 컨테이너로 실행하는 관계를 이해합니다.
- **컨테이너 운영:** ECS가 컨테이너 배치, 상태 확인, 장애 복구를 관리하는 방식을 설명합니다. 서버를 직접 관리하는 EC2 시작 유형과 서버 관리 없이 컨테이너를 실행하는 Fargate의 차이를 비교합니다.
- **마이크로서비스:** 모든 기능을 하나의 코드베이스에서 운영하는 모놀리식 구조와 기능별로 나눈 구조를 비교합니다. 특정 기능만 독립적으로 배포·확장할 수 있도록 서비스를 분리하는 이유를 설명합니다.
- **권한 분리:** 애플리케이션이 AWS 서비스에 접근할 때 사용하는 태스크 역할과, 이미지를 가져오고 컨테이너 실행을 준비하는 데 사용하는 태스크 실행 역할을 구분합니다. 각 역할에 필요한 최소 권한을 설명합니다.
- **안전한 배포:** 전체를 한 번에 교체하는 배포의 위험을 이해하고, 롤링 업데이트와 블루/그린 배포가 위험을 줄이는 방식을 비교합니다. 상태 확인을 바탕으로 실패를 감지하고 이전 버전으로 되돌리는 과정을 설명합니다.

수동 SSH 배포와 평문으로 저장된 비밀번호의 위험을 짚어내고, 컨테이너화·CI/CD 파이프라인·안전한 배포 전략을 조합해 개선안을 설계하는 것이 목표입니다.

## 학습 범위

아래 5개 서비스가 필수 학습 범위입니다. 문제 해결에 필요한 서비스는 추가로 활용할 수 있습니다.

- **ECS (Fargate):** 태스크 정의, 서비스와 원하는 태스크 수, 서비스 자동 확장, EC2 시작 유형과의 차이
- **ECR:** 이미지 저장소, 태그 전략, 수명 주기 정책, 이미지 가져오기 권한
- **IAM:** 태스크 역할과 태스크 실행 역할, 최소 권한 정책
- **Secrets Manager:** 자격 증명 저장·주입·교체, 애플리케이션의 비밀 정보 관리 방식
- **CodePipeline:** 빌드·배포 단계의 연결과 자동화, ECS 배포 단계에서의 롤링 업데이트·블루/그린 배포 및 상태 확인 기반 롤백

## 문제 상황 예시

아래는 학습 범위를 적용해 볼 수 있는 설계 예시입니다.

### 배포할 때마다 멈추는 협업 도구

SSH로 접속해 수동 배포할 때마다 서비스가 5분씩 중단됩니다. 실패한 배포를 되돌리는 데 40분이 걸리고, DB 비밀번호도 서버에 평문으로 저장되어 있습니다.

컨테이너 이미지 관리와 배포 자동화를 어떻게 연결할지 검토합니다. 중단을 줄이는 배포 전략과 실패 시 롤백, 자격 증명 관리 방식을 함께 설계합니다.

### 결제 때문에 전체 서버를 늘리는 배달 서비스

주문·결제·가게 관리가 하나의 코드베이스에 묶여 있어 결제 트래픽이 몰리면 전체 서버를 늘려야 합니다.

기능별로 서비스를 분리하고, 결제 기능만 독립적으로 확장·배포할 수 있도록 컨테이너 구성과 서비스 자동 확장 방식을 설계합니다.
