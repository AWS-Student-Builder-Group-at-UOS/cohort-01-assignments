## 준비물과 명령

기본 트랙에 필요한 도구와 권한이다. 에이전트 트랙의 준비물은 아래 에이전트 트랙 절에 있다.

| 구분 | 내용 |
|---|---|
| 계정 | 루트가 아닌 IAM 사용자와 CLI 로그인. 만드는 순서는 위 단계별 가이드의 "AWS 계정과 CLI 로그인"에 있다. `aws sts get-caller-identity`로 확인한다 |
| 도구 | [AWS CLI v2](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html), [SAM CLI](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html), Python 3.9 이상, macOS·Linux는 `make`도 필요하다. macOS에서 `make`가 없다고 나오면 `xcode-select --install`로 명령줄 도구를 설치한다 |
| 대안 | AWS 콘솔의 CloudShell에서 압축을 풀고 `make doctor`로 현재 도구·로그인을 확인한다. 신청 화면은 내 컴퓨터에서 연다 |
| 런타임 | Lambda 런타임은 Python 3.12이다. 외부 패키지 설치나 `sam build`가 필요 없는 코드이므로 배포 컴퓨터에 Python 3.12·Docker를 추가 설치하지 않아도 된다 |
| 권한 | CloudFormation, Lambda, API Gateway, DynamoDB, EventBridge, SQS, CloudWatch Logs와 IAM 역할 생성/전달 등. 배포 시작 단계의 권한 오류(첫 배포의 SAM 공용 스택 생성 등)는 터미널에, 스택 생성 중의 권한 오류는 CloudFormation Events에 나온다 |

모든 명령은 `source/` 폴더에서 실행한다. 기본 스택은 `event-signup`, 리전은 서울(`ap-northeast-2`)이다. 같은 계정을 공유하면 **사람마다 스택 이름을 다르게** 정한다. macOS·Linux·CloudShell은 아래처럼 정하고 배포·조회·삭제에 같은 값을 쓴다.

```bash
export STACK=event-signup-yourname
export REGION=ap-northeast-2
```

Windows PowerShell에는 `make`가 없다. 같은 일을 하는 PowerShell 명령은 Windows 가이드의 "스택 이름과 리전" 블록을 창마다 붙여 넣으면 쓸 수 있고, 이 문서의 `make` 명령과 아래처럼 대응한다.

| 이 문서 (`make`) | Windows PowerShell |
|---|---|
| `make doctor` | `Test-Setup` |
| `make test` | `py -m unittest -b tests.test_handlers -v` |
| `make test-exercise` | `py -m unittest -b tests.test_exercise -v` |
| `make step1` | `Deploy-Step1` |
| `make step2 DELAY=6` | `Deploy-Step2 -Delay 6` |
| `make url` | `Get-Out ApiUrl` |

| `make logs F=IssueFunction` | `Show-Logs IssueFunction` |

신청 화면은 `web/index.html`을 바로 열지 않고 로컬 서버로 연다. 파일로 열면 브라우저가 출처를 `null`로 보내 이 실습 API 호출이 CORS 오류로 막히는 것이 확인되었다. 새 터미널 창에서 `source/` 폴더로 가서 아래를 실행하고(Windows는 `py -m http.server 8000 --directory web`) 브라우저에서 `http://localhost:8000/`을 연다.

```bash
python3 -m http.server 8000 --directory web
```

## 트랙 구분

두 트랙을 비교한 표이다. 한 트랙만 해도 되고, 두 트랙을 함께 제출해도 된다(1인 1PR). 함께 제출할 때는 README의 같은 네 섹션 안에서 트랙별로 나눠 쓰고, C1–C4와 A1–A3를 각각 판정한다. 이미지 파일명은 `c1-…`, `a1-…`처럼 트랙 접두사를 붙이면 구분하기 쉽다.

| 항목 | 기본 트랙 | 에이전트 트랙 (선택) |
|---|---|---|
| 하는 일 | 핸즈온 서비스(행사 신청과 참가증 발급)를 배포하고 관찰한다 | 내가 필요한 일을 하는 Slack + LLM 에이전트를 만든다 |
| 완료 조건 | **C1–C4** | **A1–A3** |
| 배포 대상 | `source/`의 `step2/` | `agent-skeleton` (`source.zip` 안의 `agent-skeleton/` 폴더) |
| 입구 | API Gateway | Lambda Function URL (Slack 슬래시 명령) |
| 비동기 연결 | EventBridge → SQS | SQS |
| 중복 방지 | DynamoDB 조건부 쓰기 | 제공하지 않음 (A3에서 직접 설계하고 설명) |
| 비용 | 거의 없음 | 모델 호출마다 비용 발생, 한도 설정 필수 |
| 스택 이름 | `event-signup-영문이름` | 예: `my-agent` |

- 평가 기준과 배점은 두 트랙이 같다. 선택한 트랙의 완료 조건으로 판정한다.
- 에이전트 트랙을 선택했다는 이유로 가점이나 감점은 없다. 두 트랙을 함께 제출해도 가점은 없다.
- 에이전트 트랙은 모델 호출 비용이 들고 Slack 앱이 필요하므로, 기본 트랙을 먼저 해 보고 고르는 것을 권장한다.

- [ ] 이미지 속 핵심 값(응답 코드, 시간, 상태, 횟수, 비용)을 본문에도 글로 기록한다
- [ ] 로그 시각의 시간대(UTC/KST)를 표기한다
- [ ] 캡처에서 계정 ID, 액세스 키, 이메일, Signing Secret, 웹훅 주소를 가린다
- [ ] 발표자 시연 화면은 내 증거로 쓰지 않는다

## 기본 트랙

핸즈온에서 사용한 서비스(`source/`)를 내 AWS 계정에 배포하고, 아래 네 가지(C1–C4)를 **내 스택에서 직접 확인**한다. 핸즈온 중 내 스택에서 캡처한 화면이 있으면 그대로 사용할 수 있다.

### 환경

| 항목 | 내용 |
|---|---|
| 스택 이름 / 리전 | `event-signup-영문이름` / 서울(`ap-northeast-2`) |
| 데이터 | 가상 이름·이메일만 사용한다 (실습 API에는 인증이 없다) |
| 신청 화면 | `web/`을 제공한다(로컬 서버로 연다). `curl`이나 직접 만든 화면도 사용할 수 있다 |

### 열어볼 파일

네 개의 파일을 읽으면 흐름을 설명할 수 있다.

| 파일 | 볼 것 |
|---|---|
| `step2/src/register.py` | 접수: 조건부 저장 → 이벤트 발행 → `202` |
| `step2/src/issue.py` | 발급: 큐에서 꺼내기, `save_badge`의 조건부 쓰기 |
| `step2/template.yaml` | 설정값이 모여 있는 곳 |
| `step2/src/common.py` | 이벤트 발행과 입력 검증 |

### C1 · 요청 흐름

접수 함수가 DB에 저장하고 이벤트를 발행하면, EventBridge → SQS → 발급 함수가 이어받아 결과를 기록한다. 요청 하나가 끝까지 흐르는지 확인한다.

1. 정상 신청 1건을 보내고 신청 번호를 기록한다.
2. register 로그와 issue 로그를 **같은 신청 번호**로 함께 검색한다.
3. DynamoDB에서 같은 번호의 항목을 확인한다.
4. CloudFormation Resources에서 5개 서비스가 있는지 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| register 로그 | `registration_saved`, `event_published` |
| issue 로그 | `issue_started`, `badge_saved` |
| DB | `status = ISSUED`, `badgeCode` 기록 |
| Resources | API Gateway, Lambda, DynamoDB, EventBridge, SQS(+DLQ) |

**다이어그램:** 접수 → 이벤트 → 큐 → 발급 → 저장 흐름을 직접 작성한다. 접수 시점·접수 응답·발급 완료를 구분하고, 저장 위치와 정상·실패 흐름(재시도, DLQ)을 표시한다.

### C2 · 접수와 처리의 분리

`202`는 접수 완료이며 발급 완료가 아니다. 접수 응답이 발급을 기다리지 않는지 확인한다.

1. 발급 지연을 6초로 배포한다: `make step2 DELAY=6`
2. 신청 후 접수 응답의 코드와 응답 시간을 기록한다.
3. 잠시 뒤 상태 조회로 `ISSUED`가 된 시각을 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| 접수 응답 | `202`, 6초보다 훨씬 짧은 응답 시간 |
| 상태 | 처음 `PENDING`, 잠시 뒤 `ISSUED` |
| (선택) 동기와 비교 | 핸즈온 실습 1의 `201` 응답 시간과 비교 |

**정리할 것:** 접수 응답이 발급 완료를 기다리지 않는 이유, 발급이 함수 Timeout(10초)보다 길어질 때 신청과 결과가 어긋나는 양상. 실습 1에서 지연을 늘려 실험했다면 그 결과를 사용한다.

### C3 · 중복 반영 방지

큐는 같은 메시지를 다시 전달할 수 있어 중복은 자연스러운 일이다. DB의 조건부 쓰기가 발급 결과의 중복 반영을 막는지 확인한다.

#### 같은 신청을 다시 보냈을 때

| 입력 | 이렇게 보이면 |
|---|---|
| 같은 번호 · 같은 내용 | `200`, 새 이벤트 없음 |
| 같은 번호 · 다른 내용 (선택) | `409`, 원래 신청 유지 |

#### 같은 작업을 다시 발행했을 때

1. `ISSUED`인 신청의 `badgeCode`, `issueCount`를 기록한다.
2. `작업 재전송` 후 잠시 뒤 다시 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| `badgeCode` | 재전송 전과 동일 |
| `issueCount` | 1 유지 |
| issue 로그 | `badge_already_issued_skip` |

**정리할 것:** 큐가 같은 메시지를 다시 전달할 수 있는 이유, 조건부 쓰기가 막는 범위와 막지 못하는 범위(메일·결제 같은 DB 밖의 효과).

### C4 · 실패 격리

실패한 메시지는 재시도되다가 정해진 횟수를 넘으면 DLQ로 이동한다. 실패가 격리되고 다른 신청은 계속 처리되는지 확인한다.

1. **소속을 비운 신청을 먼저** 보내고 실패 번호를 기록한다. (DLQ 도착까지 대략 3분 이상)
2. 대기하는 동안 정상 신청을 이어서 보낸다.
3. issue 로그에서 실패 번호를 검색해 오류 종류와 `receiveCount`를 확인한다.
4. SQS → DLQ → Poll for messages에서 메시지 Body의 번호를 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| 실패 신청의 접수 응답 | `202`, DB는 `PENDING` 유지 |
| issue 로그 | 오류 종류 표시, `receiveCount` 증가 |
| DLQ | 기록한 실패 번호의 메시지 도착 |
| 정상 신청 | 실패와 무관하게 `ISSUED` |

> DLQ 메시지는 삭제하지 않는다. 원본 발급 큐는 콘솔에서 Poll하지 않는다.

**정리할 것:** 실패 원인 (선택 입력인 소속을 발급 코드가 필수로 가정).

#### 권장 · 원인 수정과 재처리

소속이 선택 입력이라는 계약은 유지한 채 `issue.py`를 수정한다. `make test`와 `make test-exercise` 통과를 확인한다. 재배포 후 `make redrive`를 실행하고 **같은 신청 번호**의 `ISSUED`와 `issueCount = 1`을 확인한다. 핸즈온에서 ④–⑥은 발표자가 시연하므로 시연 화면은 내 증거로 쓰지 않는다. 직접 수행해 증거를 남기고, 복구를 확인하기 전에는 스택을 삭제하지 않는다. 핸즈온에서 직접 수정했다면 그때 캡처한 화면(수정 전 오류 로그·DLQ, 수정 후 복구)을 사용한다.

### 설정 정리

설정마다 **값 · 선택 이유 · 바꾸면 생기는 영향**을 기록한다. 제공값을 그대로 쓴 설정도 이유를 쓴다.

| 설정 | 제공값 | 이유를 쓸 때 다룰 것 |
|---|---|---|
| 함수 Timeout | 10초 | 발급 지연과의 관계 |
| VisibilityTimeout | 60초 | 처리 중 메시지를 숨기는 이유, Timeout과의 관계 |
| maxReceiveCount | 3 | 수업용과 운영용 값의 차이, 일시 장애와 코드 오류의 차이 |
| BatchSize | 1 | 여러 개를 한꺼번에 처리할 때 실패 영향의 변화 |
| DB 키 · 쓰기 조건 | `registrationId`, 조건부 쓰기 | 막는 중복과 막지 못하는 중복 |
| 이벤트 규칙 · 실행 역할 | `template.yaml`의 EventPattern, Policies | 큐로 가는 이벤트의 조건, 함수마다 권한이 다른 이유 |

AWS 권장은 가시성 제한 시간을 함수 Timeout의 최소 6배, maxReceiveCount를 최소 5로 두는 것이다. 수업의 3은 실패 관찰을 위한 값이다. ([AWS Lambda–SQS 설정](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html))

### 응용 · 판단 함수 바꿔 보기 (선택)

기본 트랙의 서비스에서 입력의 의미와 `build_badge_text` 한 함수만 바꿔 나만의 에이전트처럼 만들어 본다. 완료 조건은 기본 트랙의 C1–C4를 그대로 쓰고, 별도 조건은 없다. 예시는 학교 공지 중 공모전만 알리는 에이전트이다.

| 에이전트 단계 | 이 예시에서는 | 바꾸는 곳 |
|---|---|---|
| 입력 | `name` = 공지 제목, `email` = 알림 받을 메일(가상), `organization` = 게시판 이름(선택) | 입력 칸은 **의미만** 바꾸고, 이름은 그대로 사용 |
| 판단 · 행동 | 제목에 공모전 관련 단어가 있으면 `ALERT`, 없으면 `SKIP`, 보낼 알림 문구 생성 | `step2/src/issue.py`의 `build_badge_text` |
| 기록 | `badgeText`에 저장, 중복 반영 방지는 그대로 | `save_badge` (수정 없음) |

입력 칸 이름을 새로 지으면 `common.py`, `register.py`, `tests/`, `web/app.js`, `Makefile`까지 열두 개 파일을 동시에 고쳐야 하므로, 처음에는 의미만 바꿔 사용한다. 공지 수집(크롤링)과 Slack 전송은 이번 과제의 확인 대상이 아니며, 공지 제목을 신청 화면이나 `curl`로 직접 입력하는 것으로 충분하다.

바꾼 `build_badge_text`는 아래와 같다.

```python
KEYWORDS = ("공모전", "경진", "해커톤", "대회")    # 내가 받고 싶은 공지의 단어

def build_badge_text(detail):
    """[예시 에이전트] 공지 제목에서 공모전 관련 공지만 골라 알림 문구를 만든다."""
    title = detail["name"]                          # 공지 제목 (50자 이하)
    board = detail.get("organization", "일반")      # 게시판 (선택 입력: 없어도 동작해야 한다)

    if title.startswith("FAIL-"):                   # C4용 실패 스위치: 이 제목일 때만 일부러 실패
        raise ValueError("의도된 실패: " + title)

    hits = [k for k in KEYWORDS if k in title]
    if not hits:
        return f"SKIP | {board} | {title}"          # 관련 없는 공지: 알리지 않음
    return f"ALERT | {board} | {title} | 키워드: {', '.join(hits)}"
```

함께 고칠 것이다.

- `tests/test_handlers.py`, `tests/test_exercise.py`에서 `badgeText`를 비교하는 기대값을 새 결과에 맞게 바꾸고 `make test` 통과를 확인한다.
- 결과는 DynamoDB → Explore items의 `badgeText`에서 확인한다. (`make db`는 `badgeText`를 표시하지 않는다)

C1–C4를 이 예시로 확인하는 방법이다.

| 조건 | 이 예시에서는 |
|---|---|
| C1 | 제목 `2026 클라우드 공모전 안내`, 게시판 `학생처`로 1건 전송 → 두 로그와 DB의 `badgeText`가 `ALERT`로 시작하는지 확인한다. 제목 `수강신청 일정 안내`, 게시판 비움으로 1건 더 전송 → `badgeText`가 `SKIP`으로 시작하고 게시판은 `일반`인지 확인한다 |
| C2 | 발급 지연 6초로 배포 → `202` 응답 시간과 `ISSUED` 시각 확인 |
| C3 | 같은 공지 `작업 재전송` → `badgeText` 유지, `issueCount = 1` |
| C4 | 제목을 `FAIL-테스트`로 전송 → 재시도와 DLQ 도착 확인, 공모전 공지는 `ISSUED` 확인 |

이 응용에서 지킬 것이다.

| 대상 | 주의 |
|---|---|
| 긴 작업 | Timeout과 VisibilityTimeout을 함께 조정한다. 함수 Timeout은 가시성 제한 시간 이하로 유지한다 |
| HTTP API 제한 | 통합의 최대 제한 시간은 30초이며 증설할 수 없다 ([HTTP API 할당량](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html)) |
| Slack 전송 | 실제 전송을 붙이면 같은 메시지가 다시 전달될 때 **알림이 두 번 갈 수 있다**. DB의 조건부 쓰기는 DB 밖의 전송을 막지 못하므로 C3 "정리할 것"의 소재로 쓴다. 웹훅 주소는 비밀값이므로 코드, 스크린샷, README에 남기지 않고 환경변수로 주입한다 |
| 크롤링 | 대상 사이트의 `robots.txt`와 이용약관을 먼저 직접 확인하고 요청 빈도는 낮게 유지한다. 제공 스택에서 함수가 외부로 나갈 수 있는지도 직접 확인한다 (출제 쪽에서 미확인) |

## 에이전트 트랙 (선택)

에이전트는 이벤트를 받아 **판단 → 행동 → 결과 기록**을 하는 작업자이다. `agent-skeleton`은 Slack 슬래시 명령으로 에이전트를 시작하고, Lambda가 Bedrock의 Claude를 호출해 판단한 결과를 Slack으로 돌려주는 최소 뼈대이다. 처음에는 시각과 글자 수를 도구로 확인하는 샘플 에이전트가 들어 있고, 프롬프트와 도구만 바꾸면 내 에이전트가 된다. 모든 명령은 `agent-skeleton`의 `README.md`에 있고, 따라 하는 순서는 [에이전트 트랙 가이드](https://app.notion.com/p/Session-03-PR-409840c66bba80b5b464e64ada588655)에 있다.

```text
Slack /명령 ──▶ 입구 Lambda ──▶ SQS 큐 ──▶ 워커 Lambda ──▶ Bedrock (Claude)
                (서명 검증,        │ 5회 수신하면       │
                 3초 안에 응답)    ▼ DLQ              └─▶ 결과를 Slack response_url로 회신
```

### 네 칸 정의

코드를 열기 전에 글로 네 칸을 먼저 적는다. 이 단계에는 코드가 필요 없다.

| 칸 | 하는 일 | 기본 트랙 응용 | 에이전트 트랙 |
|---|---|---|---|
| 입력 | 일을 시작시키는 요청 | 신청 화면이나 `curl` → API Gateway → `register.py` | Slack 슬래시 명령 |
| 판단 | 무엇을 할지 정함 | `issue.py`의 `build_badge_text` (규칙) | Claude가 판단 (`app/prompt.py`) |
| 행동 | 판단대로 실행 | 알림 문구 만들기 | 도구 호출 (`app/tools.py`) |
| 기록 | 결과를 남김 | DynamoDB에 저장 | Slack으로 회신 (`app/entry.py`, `app/deliver.py`) |

일을 고르는 기준은 세 가지이다.

- 반복해서 하는 일이다.
- 결과가 글로 끝난다 (초안, 요약, 분류 결과).
- 마지막 판단은 사람이 한다 (게시, 발송, 결제는 에이전트가 하지 않는다).

일 아이디어 예시이다.

| 일 | 입력 | 판단 · 행동 |
|---|---|---|
| 학교 공지 중 공모전만 알리기 | 공지 제목 | 공모전 관련 단어가 있으면 `ALERT`, 없으면 `SKIP`, 알림 문구 생성 |
| 채용 공고로 기술 트렌드 보기 | 공고 제목 또는 본문 | 기술 키워드(AWS, Kubernetes, Terraform 등)를 태그로 정리 |
| PR 리뷰 초안 만들기 (운영진 예시 봇) | PR 번호 | README와 스크린샷을 읽고 붙여 넣을 수 있는 리뷰 초안 작성. 게시·승인·머지는 하지 않음 |

판단 방식은 이렇게 고른다. 규칙으로 되는 일은 규칙으로 한다.

| 방식 | 잘 맞는 일 | 비용 | 같은 입력의 결과 |
|---|---|---|---|
| 규칙 | 키워드, 길이, 형식처럼 기준을 글로 쓸 수 있는 일 | 모델 호출 비용 없음 | 항상 같다 |
| LLM | 읽고 요약하는 일처럼 기준이 다 안 써지는 일 | 호출마다 비용 발생 | 실행마다 조금씩 다를 수 있다 |

### 구성

| 구성 요소 | 하는 일 |
|---|---|
| 입구 Lambda (Function URL) | Slack 서명과 허용 사용자를 확인하고 SQS에 넣은 뒤 "접수했어요"를 바로 응답한다 (Slack은 3초 안에 응답을 요구한다) |
| SQS 큐 + DLQ | 요청을 보관한다. 워커가 오류를 던지면 같은 메시지를 큐의 가시성 제한 시간(워커 제한 시간의 6배)이 지난 뒤 다시 전달하고, 5회 수신된 뒤에는 DLQ로 보낸다 |
| 워커 Lambda | 모델을 부르기 전에 최대 비용을 예약하고, 모델과 도구를 오가며 판단하고, 결과를 회신한 뒤 실제 비용으로 정산한다 |
| DynamoDB | 하루·한 달 누적 비용 한도를 기록한다 (중복 방지용이 아니다) |
| Bedrock | Claude 호출 |

25분이 지난 메시지는 회신 주소가 곧 만료되므로 모델을 부르지 않고 건너뛴다.

| 한도 | 기본값(샘플) | 막는 것 |
|---|---|---|

### 완료 조건

| 조건 | 내용 | 충족으로 보는 증거 |
|---|---|---|
| **A1. 구성과 요청 흐름** | Slack 명령 하나가 입구 Lambda → SQS → 워커 Lambda → 모델 호출 → Slack 회신까지 흐른 것을 보인다 | 배포된 리소스 확인 화면, 입구·워커 두 함수 로그, Slack 회신 화면 |
| **A2. 접수와 처리의 분리** | 접수 응답이 모델 판단을 기다리지 않음을 보인다 | "접수했어요"와 결과가 온 시각, 입구 로그의 처리 시간 |
| **A3. 중복 실행의 통제** | 같은 요청이 여러 번 실행되어도 비용과 부작용이 통제됨을 보인다 | 같은 명령을 두 번 실행한 회신의 비용 줄, 도구의 부작용 점검 결과 또는 중복 방지 설계 설명 |

#### A1 · 요청 흐름

Slack에서 보낸 명령이 입구 Lambda를 거쳐 큐에 들어가고, 워커 Lambda가 모델을 불러 판단한 결과를 Slack으로 회신한다. 요청 하나가 끝까지 흐르는지 확인한다.

1. 슬래시 명령 1건을 실행한다 (예: `/agent 지금 몇 시야?`). 실행한 시각과 입력을 기록한다.
2. 입구 Lambda 로그에서 `enqueued in … ms`를 찾는다.
3. 워커 Lambda 로그에서 같은 시각의 실행을 확인한다.
4. Slack에 온 회신의 마지막 줄(호출 수, 추정비용)을 확인한다.
5. CloudFormation Resources에서 구성 요소가 있는지 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| 입구 로그 | `enqueued in … ms` |
| 워커 로그 | 같은 시각의 실행, 오류 없음 |
| Slack | 곧바로 "접수했어요", 잠시 뒤 같은 대화로 답, 마지막 줄에 호출 수와 추정비용 |
| Resources | Lambda(입구, 워커), SQS(+DLQ), DynamoDB(지출 상한 표), Function URL |

**다이어그램:** 명령 → 접수 → 큐 → 워커 → 모델 → 회신 흐름을 직접 작성한다. 접수 응답과 최종 회신을 구분하고, 비용 한도 기록 위치와 실패 흐름(재시도, DLQ, 25분 건너뛰기)을 표시한다.

#### A2 · 접수와 처리의 분리

"접수했어요"는 접수 완료이며 판단 완료가 아니다. 모델이 오래 걸려도 Slack의 3초 응답 제한에 걸리지 않는지 확인한다.

1. 명령을 실행하고 "접수했어요"가 온 시각을 기록한다.
2. 결과가 온 시각을 기록한다.
3. 입구 로그의 `enqueued in … ms` 값을 기록한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| 접수 응답 | 명령 직후 "접수했어요" |
| 결과 | 접수 응답보다 늦게 같은 대화로 도착 |
| 입구 로그 | `enqueued in … ms`가 Slack의 3초 제한보다 훨씬 짧음 |

**정리할 것:** 접수 응답이 모델 판단을 기다리지 않는 이유, 워커 제한 시간(300초)과 큐 가시성 제한 시간(1800초, 6배)의 관계.

#### A3 · 중복 실행의 통제

큐는 같은 메시지를 다시 전달할 수 있고, 이 뼈대에는 DB 조건부 쓰기가 없다. 같은 요청이 두 번 실행될 수 있다는 전제에서 비용과 부작용이 통제되는지 확인한다.

1. 같은 명령을 연달아 두 번 실행한다.
2. 두 회신의 마지막 줄에서 호출 수와 추정비용을 각각 기록한다.
3. 내 에이전트의 도구(`app/tools.py`)에 부작용이 있는지 점검한다. 메일 발송, 결제, 글 게시, 외부에 쓰기가 해당한다.
4. (선택) 한도를 낮춰 재배포한 뒤 한도를 넘는 요청을 보내 안내 메시지를 확인한다.

이렇게 보이면 된다.

| 확인 항목 | 이렇게 보이면 |
|---|---|
| 두 번 실행 | 실행마다 비용이 따로 기록된다 |
| 부작용 | 없음(도구가 읽기 전용이며 그 근거를 적음), 또는 한 번만 일어나게 직접 설계한 방식과 그 설명 |
| (선택) 한도 초과 | "사용 한도에 도달해서 실행하지 않았어요" 안내가 오고 모델을 부르지 않음 |

**정리할 것:** 같은 요청이 두 번 실행될 수 있는 이유, 이 뼈대가 막는 것(비용 합계)과 막지 못하는 것(메일·결제 같은 DB 밖의 효과).

### 설정 정리

설정마다 **값 · 선택 이유 · 바꾸면 생기는 영향**을 기록한다. 제공값을 그대로 쓴 설정도 이유를 쓴다.

| 설정 | 제공값 | 이유를 쓸 때 다룰 것 |
|---|---|---|
| 워커 제한 시간 | 300초 (제공값 고정) | 모델 호출에 걸리는 시간, 가시성 제한 시간과의 관계 |
| 큐 가시성 제한 시간 | 1800초 (워커 제한 시간의 6배) | 처리 중 메시지를 숨기는 이유, 재시도 간격 |
| maxReceiveCount | 5 | AWS 권장 최소 5, 25분 건너뛰기와의 관계 |
| 입구 인증 | Function URL 인증 없음 + 코드 안의 Slack 서명 검증 | 인증 없는 주소를 서명 검증으로 대신하는 이유 |
| 허용 사용자 | `AllowedSlackUserIds` | 비우면 아무도 쓰지 못하는 이유 |
| 비용 한도 | 1회 $0.5 / 하루 $2 / 한 달 $10 | 내 값과 이유, 첫 실행의 `추정비용`으로 보정한 근거 |
| 동시 실행 | 2 | 요청이 몰려도 모델 호출이 늘지 않게 하는 이유 |
| 도구 호출 / 턴 | 12회 / 8턴 | 도구 호출이 끝없이 반복되는 루프 방지 |

AWS 권장은 가시성 제한 시간을 함수 Timeout의 최소 6배, maxReceiveCount를 최소 5로 두는 것이다. ([AWS Lambda–SQS 설정](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html))

### 주의

에이전트 트랙에서 지킬 것이다.

| 대상 | 주의 |
|---|---|
| 비밀값 | Signing Secret, 웹훅 주소, 토큰, 키는 코드·스크린샷·README·채팅에 남기지 않는다. 배포 명령의 입력칸에만 넣고, `sam deploy --guided`의 "Save arguments to configuration file"에는 `n`으로 답한다. 설정 방법은 Slack 공식 문서를 직접 확인한다 |
| 허용 사용자 | `AllowedSlackUserIds`는 내 ID로만 정한다. 비우면 아무도 쓰지 못한다 |
| 비용 | 한도를 정하고, 쓰지 않을 때는 스택을 지운다. 크레딧이 Bedrock의 Claude에 적용되는지는 약관마다 다르므로 확인하기 전에는 카드로 청구될 수 있다고 보고 한도를 낮게 시작한다 |
| LLM 사용 가능 여부 | 계정·리전·모델 권한을 `probe_models.py`로 먼저 확인한다. 학생 계정에서 가능한지는 출제 쪽에서 미확인이다 |
| 부작용 | 같은 메시지가 다시 전달되면 알림이 두 번 갈 수 있다. DB의 조건부 쓰기는 DB 밖의 전송을 막지 못하므로 A3 "정리할 것"의 소재로 쓴다. 메일 발송, 결제, 글 게시는 사람이 마지막에 한다 |
| 프롬프트 주입 | 사용자 입력과 도구 결과는 데이터로 다루라고 프롬프트에 적지만 주입을 막는다고 보장하지는 않는다. 행동을 사람이 확인하는 구조가 마지막 방어선이다 |
| 결과 검증 | 모델이 쓴 글은 그대로 믿지 않는다. 코드가 확인할 수 있는 부분은 코드가 확인하고, 확인할 수 없는 부분은 "사람이 직접 확인할 곳"으로 결과에 적는다 |
| 크롤링 | 대상 사이트의 `robots.txt`와 이용약관을 먼저 직접 확인하고 요청 빈도는 낮게 유지한다. 제공 스택에서 함수가 외부로 나갈 수 있는지도 직접 확인한다 (출제 쪽에서 미확인) |
